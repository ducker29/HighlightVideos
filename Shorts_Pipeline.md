# Техническое задание: добавление YouTube Shorts в Highlight Video Pipeline

## 0. Роль и правила работы агента

Ты — инженер, дорабатывающий существующее локальное Windows-приложение на Python/Tkinter для автоматического создания хайлайтов из разговорных YouTube-стримов.

**Цель:** добавить создание вертикальных Shorts 9:16 как второй независимый формат, сохранив существующую систему горизонтальных хайлайтов 16:9.

Основной документ проекта: `Highlight_Video_Pipeline.md`.

Перед любыми изменениями изучи актуальные файлы проекта. Документация может не полностью соответствовать последнему состоянию исходного кода.

### Обязательные правила

1. Работай строго по этапам, описанным ниже.
2. За один рабочий цикл выполняй только один этап или небольшую его часть.
3. Перед изменением файла прочитай его актуальное содержимое и связанные интерфейсы.
4. Не переписывай большие модули целиком, если достаточно локального изменения.
5. Не изменяй существующую логику длинных хайлайтов без технической необходимости.
6. Не удаляй старые отчёты, кеши, результаты рендера и утверждения пользователей.
7. Не выполняй повторное скачивание VOD или транскрипцию, если подходящие артефакты уже существуют.
8. Не меняй используемые LLM без отдельного разрешения.
9. Не устанавливай новые тяжёлые зависимости без обоснования.
10. Не считай задачу завершённой без проверок.
11. Не утверждай, что тест прошёл, если он фактически не запускался.
12. После завершения этапа предоставь отчёт и остановись до следующего разрешения.

### Формат отчёта после каждого этапа

- Что реализовано.
- Какие файлы изменены и почему.
- Какие существующие механизмы переиспользованы.
- Какие тесты выполнены и их фактические результаты.
- Что не удалось проверить.
- Какие риски и ограничения остались.
- Что предлагается делать на следующем этапе.

При ошибке сначала исследуй её причину. Не заменяй строгую проверку ослабленным условием ради прохождения теста.

# ЭТАП 2. Профили форматов и структура данных

**Цель:** разделить параметры длинных хайлайтов и Shorts без дублирования общего пайплайна.

## 2.1. Профили обработки

Предлагаемая логическая структура конфигурации:

```json
{
  "outputs": {
    "highlights": {
      "enabled": true,
      "min_duration_sec": 120,
      "target_duration_sec": 180,
      "max_duration_sec": 300,
      "aspect_ratio": "16:9",
      "max_candidates": 25
    },
    "shorts": {
      "enabled": false,
      "min_duration_sec": 20,
      "target_duration_sec": 40,
      "max_duration_sec": 60,
      "aspect_ratio": "9:16",
      "max_candidates": 30,
      "final_candidates": 10,
      "subtitles_enabled": true,
      "crop_mode": "center"
    }
  }
}
```

Это предлагаемая схема, а не требование немедленно заменить существующий `config.json`.

Агент должен выбрать способ миграции, который сохраняет старые настройки. При отсутствии новых ключей старый режим должен продолжать работать.

По умолчанию Shorts отключены, пока их функциональность не проверена.

## 2.2. Общие и раздельные данные

Общие данные одного VOD:

- исходный файл;
- метаданные видео;
- аудио;
- транскрипт и word timestamps;
- технические окна;
- результаты PASS 1;
- тематические блоки.

Раздельные данные:

- результаты отбора длинных хайлайтов;
- результаты отбора Shorts;
- редакционные проверки;
- статусы кандидатов;
- утверждения;
- настройки рендера;
- экспортированные файлы.

## 2.3. Формат кандидата

Предлагаемая структура:

```json
{
  "candidate_id": "s001",
  "format": "short",
  "source_video_id": "VIDEO_ID",
  "start": 100.5,
  "end": 143.2,
  "title": "Пример названия",
  "score": 85,
  "status": "pending",
  "interval_id": "short_iv_001",
  "render_settings": {
    "profile": "vertical_9_16",
    "crop_mode": "center",
    "crop_x": null,
    "subtitles_enabled": true
  }
}
```

Существующие кандидаты без поля `format` должны интерпретироваться как `highlight`.

Идентификаторы должны быть стабильными внутри отчёта. Для Shorts и длинных хайлайтов следует использовать отдельные пространства идентификаторов или явно проверять уникальность.

## 2.4. Утверждения

Утверждение Short должно быть независимо от утверждения длинного хайлайта.

Изменение любого параметра, влияющего на итоговый MP4, должно требовать повторного утверждения соответствующего результата:

- начало;
- конец;
- концевой запас;
- режим кадрирования;
- координаты кадрирования;
- субтитры и их содержимое;
- существенные параметры компоновки.

При этом изменение названия файла само по себе не должно автоматически менять утверждённые временные границы, если существующая архитектура уже отделяет метаданные от видеосодержимого.

Реализовать детерминированную сигнатуру утверждаемого результата, учитывающую параметры, действительно влияющие на экспорт.

## 2.5. Совместимость

Проверить:

- открытие старых отчётов;
- сохранение старых отчётов без потери полей;
- корректную работу существующих утверждений;
- индивидуальный рендер;
- массовый рендер;
- концевой запас;
- существующие имена файлов.

**Критерий готовности:** добавлены профили и структура данных, но существующий рендер и UI продолжают работать без изменений поведения.

# ЭТАП 3. Поиск кандидатов Shorts

**Цель:** научить систему находить короткие самостоятельные сюжеты в транскрипте.

## 3.1. Точка разделения

Использовать существующие результаты PASS 1 и тематического объединения.

Не запускать повторно Whisper и PASS 1, если данные доступны в совместимом кеше.

Создать отдельный проход `Shorts Selection`, который не зависит от финального списка длинных хайлайтов.

## 3.2. Источники кандидатов

Использовать:

- `strong_moments` из PASS 1;
- высокие значения `hook_score`;
- `emotion_score`;
- `interest_score`;
- `self_contained`;
- тематические блоки;
- реальные границы предложений и слов.

Дополнительно искать самостоятельные короткие мысли, которые не попали в список длинных хайлайтов.

Не считать каждый `strong_moment` готовым Short: он может быть слишком коротким или зависеть от предшествующего контекста.

## 3.3. Отбор интервалов

Переиспользовать принцип существующего PASS 2A/2B:

1. Код определяет возможные начала.
2. Код строит допустимые окончания.
3. Код вычисляет фактическую длительность с учётом запаса.
4. Код присваивает стабильные `interval_id`.
5. Модель получает ограниченный каталог допустимых вариантов.
6. Модель выбирает только существующий ID либо `none`.
7. Валидатор отвергает неизвестные ID.

Не разрешать LLM самостоятельно вычислять длительность или придумывать таймкоды.

Рекомендуемые начальные ограничения:

- минимум 20 секунд;
- цель 35–45 секунд;
- максимум 60 секунд;
- не обрезать предложение ради соблюдения максимума;
- если законченный сюжет не помещается, отклонить вариант.

В дальнейшем длительность должна быть настраиваемой.

## 3.4. Критерии качества Shorts

Оценивать отдельно:

- силу первых 1–3 секунд;
- понятность без просмотра полного стрима;
- наличие одной ясной темы;
- наличие самостоятельного вывода или развязки;
- отсутствие длинного вступления;
- отсутствие лишних повторов;
- эмоциональную или информационную ценность;
- отсутствие обрыва мысли.

Не использовать без изменений формулу ranking длинных хайлайтов.

Ввести отдельную функцию оценки, например:

```text
short_score =
  0.30 * hook
+ 0.25 * self_contained
+ 0.20 * payoff
+ 0.15 * interest
+ 0.10 * speech_clarity
```

Это начальная эвристика. Её веса должны быть конфигурируемыми и проверяться на реальных результатах.

## 3.5. Дедупликация

Внутри Shorts:

- удалять временные дубликаты;
- учитывать смысловые повторы;
- не удалять сильные варианты только потому, что они пересекаются с длинными хайлайтами.

Между форматами допускается пересечение: один интересный момент может использоваться и в длинном ролике, и в Short.

## 3.6. Ограничения локальной LLM

Запросы должны быть короткими и структурированными.

Использовать:

- небольшие порции каталога;
- JSON-schema или другую существующую строгую валидацию;
- выбор из enum;
- ограниченное число повторных попыток;
- сохранение валидных результатов;
- явные причины отказа;
- отдельный кеш Shorts;
- `analysis_complete` и предупреждения при частичном результате.

Не передавать полный многочасовой транскрипт в один запрос.

Не дублировать весь контекст между последовательными вызовами, если достаточно короткого резюме и выбранного фрагмента.

## 3.7. Результат

Создать отдельный отчёт кандидатов Shorts со статусом `pending`.

На данном этапе вертикальный рендер не нужен.

**Критерий готовности:** система находит кандидатов Shorts на сохранённом транскрипте, все интервалы программно валидны, существующие длинные кандидаты не изменены.

# ЭТАП 4. Редакторская проверка и утверждения

**Цель:** обеспечить качество коротких сюжетов и защиту от случайного рендера.

## 4.1. Отдельная редакционная проверка

Расширить существующий `editorial_review.py` либо добавить специализированный модуль.

1. Понятен ли Short без предшествующего контекста?
2. Есть ли сильное начало?
3. Не обрывается ли мысль?
4. Есть ли завершение?
5. Нет ли длинной паузы в начале?
6. Нет ли перехода на другую тему?
7. Не является ли фрагмент просто обрывком хорошей истории?

Результат проверки:

- принять как кандидата;
- предложить допустимую корректировку границ;
- отправить на ручную доработку;
- отклонить.

Редакторская LLM никогда не присваивает `approved`.

## 4.2. Контекст

Переиспользовать `transcript_review.py`.

Показывать:

```text
КОНТЕКСТ ДО

-----НАЧАЛО-SHORT-----

Точный текст внутри утверждаемых границ

-----КОНЕЦ-SHORT-----

КОНТЕКСТ ПОСЛЕ
```

Частично вошедшие предложения и слова отображать по уже существующим правилам.

## 4.3. Ручные правки

Сохранить возможность:

- изменить начало;
- изменить конец;
- изменить заголовок;
- включить/выключить концевой запас;
- утвердить;
- отклонить;
- вернуть на доработку.

Не разрешать автоматическое скрытое изменение границ после утверждения.

## 4.4. Проверки

- Изменение границ снимает утверждение Short.
- Изменение Short не снимает утверждение другого кандидата.
- Старые длинные хайлайты продолжают открываться.
- Невалидный интервал не может попасть в рендер.
- Частично невалидный ответ LLM не уничтожает валидные кандидаты.

**Критерий готовности:** Shorts проходят независимое ревью и могут быть утверждены, но экспорт пока не обязателен.

# ЭТАП 6. Вертикальный рендер Shorts

**Цель:** экспортировать утверждённые Shorts в 9:16 без изменения исходного видео.

## 6.1. Базовый профиль

Предлагаемые параметры:

- контейнер MP4;
- H.264;
- AAC;
- 1080×1920;
- соотношение сторон 9:16;
- исходная частота кадров либо совместимый явно выбранный FPS;
- точные утверждённые временные границы;
- отсутствие скрытого добавления секунд.

## 6.2. Первый режим: центральное кадрирование

Реализовать в первую очередь.

Для горизонтального источника:

1. Вычислить вертикальную область 9:16.
2. Разместить её по центру исходного кадра.
3. Масштабировать до 1080×1920.
4. Сохранить пропорции без растягивания.
5. Проверить фактическое разрешение и длительность результата.

Для исходного 1280×720 центральная область 9:16 имеет размер 405×720 пикселей. Это означает сильное увеличение при экспорте в 1080×1920. Нужно предупреждать, что итоговая детализация не станет выше исходной.

## 6.3. Второй режим: ручное кадрирование

Добавить возможность смещать область кадрирования по горизонтали.

Сохранять позицию в данных конкретного кандидата.

Пользователь должен видеть результат в вертикальном предпросмотре до утверждения.

## 6.4. Третий режим: обнаружение лица

Добавить после проверки первых двух режимов.

Требования:

- использовать лёгкую модель или библиотеку;
- анализировать редкие контрольные кадры, а не каждый кадр через тяжёлую нейросеть;
- находить устойчивое положение говорящего;
- не создавать резких перемещений кадра;
- при неуверенном обнаружении использовать центральное кадрирование;
- разрешать ручную коррекцию.

Не вводить тяжёлый трекинг лица в первую версию.

## 6.5. Альтернативная компоновка

Предусмотреть в будущем режим:

- исходный горизонтальный кадр полностью виден;
- вертикальный холст заполнен размытым фоном;
- лицо и важные элементы не обрезаются.

Этот режим полезен, когда говорящий находится не по центру или в кадре присутствует важный текст.

## 6.6. Субтитры

Использовать существующие word timestamps.

На первом этапе:

- разбивать текст на короткие читаемые фразы;
- не показывать слишком много слов одновременно;
- располагать текст в безопасной области кадра;
- использовать контрастную обводку;
- учитывать вертикальный размер видео;
- поддерживать кириллицу;
- не добавлять слова за пределами фактического интервала.

Не запускать повторное распознавание речи ради субтитров.

В первой версии достаточно одного качественного стиля. Анимацию каждого слова добавить позже.

## 6.7. Проверка экспорта

После FFmpeg проверять:

- наличие MP4;
- успешное декодирование;
- размер 1080×1920;
- наличие аудио;
- фактическую длительность с заданной допустимой погрешностью;
- отсутствие чёрного или пустого кадра на тестовых отрезках;
- сохранение утверждённых границ;
- корректную синхронизацию субтитров.

## 6.8. Пути экспорта

```text
data/VIDEO_ID/output/
  highlights/
    c001_Название.mp4
  shorts/
    s001_Название.mp4
```

Не перезаписывать существующие файлы без явного разрешения.

**Критерий готовности:** утверждённый Short экспортируется в 9:16 с правильными границами, аудио и субтитрами.

# ЭТАП 7. Интеграция и регрессионные тесты

**Цель:** убедиться, что расширение не ухудшило существующую систему.

## 7.1. Тесты форматов

Проверить:

- только highlights;
- только Shorts;
- оба формата;
- повторный запуск только Shorts;
- повторный запуск только highlights;
- повторное использование общего кеша;
- открытие старого отчёта;
- открытие нового отчёта;
- независимое утверждение;
- независимый рендер.

## 7.2. Тесты интервалов

Проверить:

- минимум и максимум;
- отказ при отсутствии допустимого окончания;
- выбор только разрешённого `interval_id`;
- недопустимый ID;
- концевой запас;
- конец у границы исходного VOD;
- частично вошедшее предложение;
- ручную правку;
- пересечение кандидатов.

## 7.3. Тесты LLM

Проверить:

- невалидный JSON;
- пустой ответ;
- `none`;
- неверный ID;
- слишком большой запрос;
- частично валидный список;
- три неудачные попытки;
- восстановление из кеша;
- частичный отчёт с предупреждениями.

## 7.4. Тесты UI

Проверить:

- переключение вкладок;
- сохранение настроек;
- редактирование кандидата;
- снятие утверждения;
- индивидуальный рендер;
- массовый рендер;
- закрытие приложения во время фоновой операции;
- открытие старых отчётов;
- ввод и вставку текста при русской раскладке.

## 7.5. Тесты видео

Проверить на синтетическом и реальном материале:

- горизонтальный рендер 16:9;
- вертикальный рендер 9:16;
- ручной и центральный кроп;
- субтитры;
- длительность;
- разрешение;
- звук;
- отсутствие перезаписи предыдущих результатов.

**Критерий готовности:** существующие тесты проходят, новые тесты проходят, оба формата работают независимо.

# ЭТАП 8. Проверка на реальном стриме

**Цель:** оценить не только техническую корректность, но и качество Shorts.

## 8.1. Исходные данные

Использовать уже скачанный и транскрибированный тестовый VOD из проекта.

Не скачивать его повторно, если локальный файл доступен.

Сначала протестировать диапазон 30 минут, затем при успешном результате перейти к полному видео.

## 8.2. Ручная оценка

Для каждого Short оценить:

- понятность без контекста;
- силу начала;
- завершённость;
- интересность;
- отсутствие лишних пауз;
- правильность таймкодов;
- качество кадрирования;
- читаемость субтитров.

Использовать простую шкалу 1–5.

## 8.3. Сравнение с длинными хайлайтами

Определить:

- сколько Shorts найдено независимо;
- сколько Shorts находятся внутри длинных хайлайтов;
- сколько сильных моментов длинная ветка пропустила;
- сколько коротких кандидатов пришлось отклонить;
- сколько времени занял анализ;
- сколько времени занял рендер;
- сколько ручной работы потребовалось.

## 8.4. Финальный отчёт

Создать `SHORTS_VALIDATION_REPORT.md`:

- параметры запуска;
- используемые модели;
- сведения о кеше;
- число кандидатов;
- число утверждённых;
- число отклонённых;
- причины отклонений;
- результаты ручной оценки;
- время выполнения;
- обнаруженные ошибки;
- рекомендации по дальнейшей настройке.

Не заявлять, что система готова к коммерческому использованию, пока не проверены реальные готовые Shorts.

# Общие критерии завершения проекта

Работа считается завершённой, когда:

1. Существующие длинные хайлайты продолжают работать без регрессий.
2. Shorts можно запускать независимо.
3. Оба формата используют общий транскрипт и общий предварительный анализ.
4. Shorts находятся независимо от списка длинных хайлайтов.
5. Модель не придумывает таймкоды.
6. Каждый кандидат проходит программную валидацию.
7. Есть отдельное ручное утверждение Shorts.
8. Интерфейс позволяет просматривать оба формата.
9. Вертикальный предпросмотр соответствует финальному рендеру.
10. Субтитры используют сохранённые таймкоды.
11. Финальные Shorts экспортируются в 9:16.
12. Старые отчёты, утверждения и файлы не повреждены.
13. Все фактически выполненные тесты документированы.
14. Качество проверено на реальном разговорном стриме.
