# Локальный горизонтальный Highlight Pipeline

Новый сценарий запуска: `main.py`. Исходные Colab-скрипты сохранены для справки;
`pipeline.py`, `clip_renderer.py`, `ollama.py` и `link_drive.py` не используются приложением.
Локальный `ollama.py` не импортируется: общение с уже установленной Ollama идёт через HTTP.

## Установка и запуск (PowerShell)

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

После установки можно запускать двойным щелчком `start_gui.bat`.
Скрипт использует локальное виртуальное окружение `.venv` без ручной активации
и открывает приложение в отдельном процессе с собственным окном консоли.
Рабочая папка автоматически устанавливается в корень проекта, поэтому запуск
работает также через ярлык или из другой папки. Закрытие исходного терминала
не закрывает приложение. Консоль приложения оставляйте открытой до завершения работы.
Для перезапуска закройте приложение и снова запустите `start_gui.bat`.
Скрипт также принимает аргументы: `start_gui.bat --report "ПОЛНЫЙ_ПУТЬ_К_report.json"`.
Если `.venv` отсутствует, он покажет подсказку об установке и дождётся нажатия клавиши.
Проверки: `.venv\Scripts\python.exe -m unittest discover -v`.

В PATH нужны `ffmpeg`, `ffprobe` и, для просмотра интервалов, `ffplay`.
Ollama должна быть запущена; её установка и скачивание LLM автоматически не выполняются.
Нажмите «Обновить модели» и выберите установленную **текстовую** модель, не embedding-модель.
По умолчанию выбрана имеющаяся на этом компьютере `deepseek-r1:latest`.
Она выполняет первичный анализ; в поле «LLM-редактор» выбрана уже установленная
`tom_himanen/deepseek-r1-roo-cline-tools:14b` для отдельной проверки кандидатов.
Обе модели можно поменять в UI. Подробный результат реального теста первых 30 минут,
включая выявленные проблемы смысловых границ: [VALIDATION_REPORT.md](VALIDATION_REPORT.md).

Whisper при первом запуске загрузит веса выбранной ASR-модели.
Веса сохраняются внутри проекта: `data/models/whisper`, а не в глобальный кеш.
Для CUDA установите локальные библиотеки:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-cuda.txt
```

`gpu_runtime.py` подключает DLL из `.venv` только к текущему процессу.
Системный PATH и драйвер NVIDIA не изменяются. Для CPU установка GPU-пакетов не нужна.
Нужен совместимый драйвер NVIDIA; на текущем компьютере GPU-тест прошёл на драйвере 616.92.
Для быстрой проверки можно выбрать Whisper `small`, для основного качества — `large-v3`.
PyAV закреплён на 16.1.0: PyAV 19 несовместим с используемым Faster-Whisper 1.2.1.

В текущей сети прямое извлечение диапазона FFmpeg из YouTube зависало; скачивание
аудиодорожки обычным загрузчиком yt-dlp с локальным извлечением работает.
Результаты: `data/gpu_smoke/start_300_duration_60/`, включая `result_small.json`.

без учёта скачивания аудио/весов. Это проверка инфраструктуры, не оценка точности ASR.
`large-v3` и полный VOD этим тестом ещё не проверялись.
После обновления приложения перезапустите ранее открытое окно через `start_gui.bat`.

### Полный VOD и проверка первых 30 минут на large-v3

```powershell
.\.venv\Scripts\python.exe validate_vod.py --stage download
.\.venv\Scripts\python.exe validate_vod.py --stage model
.\.venv\Scripts\python.exe validate_vod.py --stage analyze
```

Этапы сохраняют отдельные журналы, статусы и результаты в
`data/validation_runs/AVbz4UzkeTw_first30/`. Веса и полный исходник кешируются.
`--stage analyze --wait` может ждать завершения отдельно запущенных download/model.
Стадия анализа использует только 00:00–30:00, но сохраняет абсолютные таймкоды
и ссылку на полный исходник для просмотра и будущего рендера.
Тестовые данные изолированы в `data/AVbz4UzkeTw/validation_first30/`, чтобы
не перепутать частичный транскрипт с результатом обработки целого VOD.
Перед ASR выгружается только выбранная приложением LLM, чтобы освободить VRAM.
Финальные клипы не создаются; отчёт остаётся на стадии ревью.

Готовый отчёт можно открыть кнопкой в UI либо командой:

```powershell
.\.venv\Scripts\python.exe main.py --report "ПОЛНЫЙ_ПУТЬ_К_report.json"
```

UI показывает диапазон фактически выполненного анализа. При загрузке отчёта
настройки длительности и моделей переключаются на параметры этого отчёта.

После PASS 2 выполняется независимая редакционная проверка (`editorial_review.py`):
модель получает выбранный клип отдельно от 90-секундного контекста ДО/ПОСЛЕ,
может сохранить, уточнить границы либо отклонить заявку. После правок снова
проверяются длительности и пересечения. Это не человеческое утверждение:
все оставшиеся кандидаты имеют статус `pending`.
Исходные кандидаты, попытки исправления JSON и редакционные решения сохраняются
для диагностики. Причины отклонений выводятся в журнал UI при открытии отчёта.
Редакционный кеш зависит от модели; контекст редактора — 16384 токена.
При наличии `quality_notes.json` рядом с `source.json` UI показывает замечания
тестового прогона только для совпадающих границ; после правки интервала старые
замечания к границам больше не показываются и не сохраняются в решение редактора.

## Работа

1. Вставьте YouTube-ссылку **или** укажите файл в поле **«Локальный файл (приоритет)»**
   прямо под ссылкой (кнопка **«Обзор…»** открывает выбор файла).
   Заполненный локальный путь имеет приоритет, даже если ссылка тоже указана.
   Для возвращения к YouTube очистите поле пути. Тестовый VOD уже задан в `config.json`.
   Для замены текущей ссылки используйте **Ctrl+A → Ctrl+V**. Сочетания работают
   и в русской раскладке Windows. Также доступны правое меню «Вставить» и кнопка
   **«Вставить»** рядом с полем: кнопка заменяет ссылку целиком текстом из буфера.
   Пустой или нетекстовый буфер не стирает существующую ссылку.
2. Укажите минимальную и максимальную длительность в секундах: обычно 120–300,
   максимум 480. Это ограничения для смыслового отбора, не размер технических окон.
   Настройка «Запас в конце, с» по умолчанию равна **0,5**; можно выбрать 1 секунду
   или ввести значение 0–5 с (0 отключает запас). Запас применяется после смыслового
   отбора **до ревью**, поэтому таблица, FFplay и рендер используют одну итоговую границу.
3. Выберите область анализа в строке `[✓] Анализ полного видео — с … до … мин`.
   При включённом чекбоксе анализируется весь VOD, поля минут неактивны и игнорируются.
   При выключенном задайте начало/конец в минутах от начала источника (например, 15–45).
   Допускаются дробные минуты и десятичная запятая. Диапазон должен находиться внутри видео.
   Это отдельная настройка от длительности клипов в секундах. Настройки сохраняются;
   границы диапазона учитываются в кеше ASR и анализа. Таймкоды остаются абсолютными.
4. Нажмите **«Анализировать видео»**. Нарезка на этом этапе **не выполняется**.
5. Просмотрите таблицу, обоснование и транскрипт. Первая колонка «ID» содержит
   идентификатор кандидата (`c001`, `c002` и т. д.). FFplay открывает выбранный интервал
   исходного видео без предварительного рендера.
6. При необходимости измените начало/конец (секунды или `ЧЧ:ММ:СС.ммм`) и заголовок.
   «Сохранить правки / на доработку» снимает утверждение. «Утвердить интервал»
   сохраняет и утверждает текущие границы. «Отклонить» исключает кандидата из нарезки.
7. Нажмите «Нарезать утвержденные клипы» и подтвердите запуск.
   Для нарезки одного утверждённого клипа нажмите **«▶ Нарезать»** в его строке таблицы.
   Остальные клипы при этом не нарезаются; общее действие по-прежнему доступно.

### Сворачиваемый блок и локальный источник

Заголовок **«▼ Источник и настройки»** — кнопка. По нажатию весь блок настроек
сворачивается (**«▶ Источник и настройки»**) или раскрывается. Значения полей сохраняются,
анализ использует их и в свёрнутом состоянии. При запуске блок раскрыт; заголовок
можно нажимать и во время обработки. Кнопки анализа, рендера и таблицы находятся вне блока.

Путь локального файла сохраняется вместе с остальными параметрами в `data/ui_settings.json`
при запуске анализа (`local_video_path`, по умолчанию пустой). Можно вставить путь в кавычках,
скопированный проводником Windows. Ссылка не требуется, если путь заполнен. Ошибка локального
пути не приводит к скрытому переходу на YouTube: приложение сообщает об ошибке.

Видео используется **на месте, без скачивания и копирования в проект**. Поддерживается
любой контейнер, который читает установленный FFmpeg; сохраняются существующие требования
к источнику: видео 16:9 и аудиодорожка. Whisper, Ollama, диапазон анализа, ручное утверждение,
субтитры, Smart Crop и настройки экспорта работают через прежний пайплайн.

Для локальных файлов создаётся `data/local_<идентификатор>/source.json` с абсолютным путём,
типом источника и SHA-256. Идентификатор зависит от полного нормализованного пути и содержимого:
одноимённые файлы из разных папок и изменённые версии не используют чужой кеш. Неизменённый
файл по прежнему пути повторно использует кеш. Старые отчёты, аудио и результаты не удаляются.
Чтобы обнаружить замену файла даже с прежними размером и временем изменения, при подготовке
анализа читается весь файл для SHA-256; на большом HDD-видео это может занять время.

Не перемещайте и не изменяйте исходник, пока он нужен для просмотра и рендера. Сохранённый
отчёт можно открыть для текстового ревью и без видео, но просмотр и экспорт требуют исходник.
Перед рендером локального источника повторно проверяется SHA-256: изменённый файл нельзя
незаметно использовать со старой транскрипцией и утверждёнными границами. Верните исходную
версию или выполните новый анализ изменённого видео.

### Скачивание YouTube: готовый поток со звуком

Для **новых** скачиваний программа выбирает только потоки, в которых видео и аудио
уже объединены. Порядок разрешений:

1. **1080p**.
2. Если 1080p нет — ближайшее доступное **выше**: 1440p, затем 2160p и т. д.
3. Если выше тоже нет — лучшее доступное **ниже**: 720p, затем 480p, 360p и т. д.

Разрешения сравниваются только среди готовых потоков со звуком. Наличие отдельного
1080p-видеопотока не означает, что доступен готовый 1080p со звуком. Например, YouTube
может предложить для конкретного VOD только совмещённый 360p; в таком случае скачивается
360p без искусственного увеличения. Выбранное и фактическое разрешения выводятся в лог.

Основной загрузчик — **yt-dlp**. При ошибке метаданных или загрузки автоматически
используется независимый **pytubefix** с тем же приоритетом разрешений и только
progressive-потоками. Если оба загрузчика не смогли получить готовый поток со звуком,
программа сообщает об ошибке; раздельные видео/аудио в качестве скрытого обхода не скачиваются.

Готовый поток упаковывается в прежний `source.mkv` **без перекодирования**. Это смена
контейнера одного файла, не объединение отдельно скачанных видео и аудио. Перед публикацией
источник проверяется через ffprobe. Каждый загрузчик использует свою временную папку:
незавершённые байты одного загрузчика не дописываются другим. Сведения о загрузчике,
формате и выбранной высоте записываются в `source.json` → `download_info`.

Ранее скачанный валидный `source.mkv` с соответствующим `source.json` используется
**без сети и без повторного скачивания**, сохраняя своё прежнее разрешение. Файлы без
манифеста или повреждённый кеш не перезаписываются автоматически. Новый порядок выбора
не меняет уже существующие источники, транскрипты, отчёты и результаты.

Зависимость `pytubefix>=11.2.1,<12` добавлена в `requirements.txt`; после получения обновлений
установите зависимости обычной командой из раздела установки. В текущей `.venv` она уже
установлена. Сетевые обрывы 10054 могут затронуть оба загрузчика: резервирование не является
гарантией обхода проблем сети. Локальные файлы работают независимо от YouTube-загрузчиков.

Проверки: `python -m unittest test_youtube_download -v` — порядок разрешений, запрет
раздельных потоков, офлайн-кеш и его защита, переключение после обрыва 10054, синтетический
файл с настоящими FFmpeg/ffprobe. Автотесты не скачивают YouTube и не запускают ASR/LLM.

В карточке и подтверждении нарезки показано имя следующего файла:
например, `c002_Гиперинфляция и политика большевиков.mp4`.
Формат — `ID_Заголовок.mp4`; используется сохранённый заголовок из таблицы,
включая ручные правки. Пробелы и русские буквы сохраняются; недопустимые в Windows
символы `\ / : * ? " < > |` и управляющие символы заменяются на `_`, лишние
пробелы объединяются, конечные пробелы/точки удаляются. Длинный заголовок
сокращается с учётом длины имени и полного пути. Пустой — «Без названия».
При совпадении MP4 или его сопроводительных файлов добавляется `_2`, `_3` и т. д.,
включая повторную нарезку того же кандидата. Предыдущие результаты сохраняются.
Изменение заголовка или границ не меняет ID. Хеш утверждённых границ хранится
во внутренних данных и JSON рядом с видео, но не включается в видимое имя.
ID уникален в пределах отчёта, а выходные файлы разных отчётов лежат в отдельных
папках `output/<signature>/`. Старые отчёты также показывают ID; диапазон анализа
восстанавливается из сохранённого транскрипта, если новых настроек в них ещё нет.

### Текст и соседние реплики в окне правок

При нарезке рядом с каждым MP4 создаётся одноимённый TXT в UTF-8: название клипа,
«Почему выбран» и реплики в том же виде, что в окне реплик — с таймкодами исходного
видео, контекстом до и после (до трёх реплик) и маркерами начала/конца клипа.
Текст соответствует итоговым утверждённым границам, включая ручные правки и запас.
Служебные данные и техническая строка об ASR в TXT не включаются; пометки неполных
реплик сохраняются. TXT создаётся и при нарезке одного клипа, и при пакетной нарезке.
При повторной нарезке прежние TXT сохраняются вместе с прежними видео.

Транскрипт в карточке отделяет содержимое клипа от соседнего контекста:

```text
КОНТЕКСТ ДО — НЕ ВХОДИТ ЦЕЛИКОМ В КЛИП
до трёх предыдущих реплик

-----НАЧАЛО-КЛИПА-----
полные реплики и явно отмеченные части реплик внутри указанных границ
-----КОНЕЦ-КЛИПА-----

КОНТЕКСТ ПОСЛЕ — НЕ ВХОДИТ ЦЕЛИКОМ В КЛИП
до трёх следующих реплик
```

Контекст отображается серым, маркеры — синим, неполные реплики — отдельным цветом.
Таймкоды относятся к исходному видео. Если граница/запас захватили только часть
реплики, её полный текст показан в контексте с явной пометкой. Внутри маркеров
выводятся только целиком попавшие слова по ASR-разметке и указание на разрезанные
слова; при отсутствии word-level данных точный текст этой части не выдумывается.
В начале/конце сохранённого транскрипта контекст может содержать меньше трёх реплик.

При вводе новых start/end текст пересчитывается сразу. Это только предпросмотр:
до «Сохранить правки»/«Утвердить» файл отчёта и прежнее утверждение не меняются.
Некорректный или ещё не дописанный таймкод временно показывает подсказку вместо
старого текста, который мог бы вводить в заблуждение. Отображение контекста само
по себе не расширяет клипы и не перерендеривает существующие MP4.

### Запас после последнего слова

В каждой строке таблицы есть кликабельный чекбокс **«Запас»** (☑ / ☐).
Количество секунд общее — поле **«Запас в конце, с»** в настройках.
Снятие галочки возвращает базовый конец, установка добавляет текущее общее значение.
Границы сразу обновляются в таблице, карточке и предпросмотре и сохраняются в отчёте.
Изменение утверждённых границ снимает утверждение: перед нарезкой утвердите клип заново.
Перед действием в строке нужно сохранить несохранённые правки карточки.
Выбор сохраняется при повторном открытии отчёта; у старых отчётов запас по умолчанию включён.
Чтобы применить новое общее число секунд ко всем включённым клипам, используйте
**«Применить запас к отчёту»**; отключённые клипы остаются без запаса.
При индивидуальном переключении после ручного изменения конца именно ручной конец
становится новой базой; автоматическое применение ко всему отчёту ручные границы сохраняет.

Для новых результатов запас добавляется автоматически. Для старого отчёта выберите
значение «Запас в конце, с» и нажмите **«Применить запас к отчёту»** (в общей строке кнопок,
между нарезкой утверждённых клипов и прогрессбаром). Повторять ASR
и LLM-анализ не нужно. Создаётся отдельный отчёт; исходный сохраняется.
Изменённые утверждённые интервалы возвращаются в `pending` и требуют нового утверждения.
Повторное применение того же значения не удлиняет клипы ещё раз; смена 0,5 → 1
считает запас от сохранённой базовой границы, а не прибавляет 1 к уже добавленным 0,5.
Сохранение ручных правок, утверждение и рендер сами запас не добавляют.
Если конец уже изменён вручную после применения запаса, автоматическая подготовка
не перезаписывает эту границу.

Итоговый конец ограничен концом исходника и максимальной длительностью клипа.
Если весь запас не помещается, в карточке появляется замечание — проверьте последнее
слово и при необходимости скорректируйте интервал. После запаса заново проверяются
длительности и временные пересечения; пересечения показываются как замечания,
кандидаты автоматически не удаляются. У конца анализируемого диапазона небольшой
запас может выйти за диапазон ASR, но не за пределы полного исходника.
В карточке видны базовый конец и фактически добавленное число секунд.
Сам рендерер использует уже утверждённую границу и не добавляет скрытого padding.

Финальный рендер использует H.264 CRF 18 / AAC 192k: это перекодирование с потерями,
а не побитовое сохранение источника. Разрешение и полный кадр 16:9 сохраняются;
кроп, растягивание и субтитры не применяются. Выход — MP4.

data/<video_id>/

  audio.wav                    моно-аудио для ASR

  state.json                   последний этап / ошибка
  analysis/<signature>/

  analysis/shorts_<signature>/
    block_*/catalog.json       каталог Shorts-интервалов (20–60 с)

  output/<signature>/          утверждённые MP4, TXT с репликами, sidecar JSON и FFmpeg-логи

Повторный запуск использует завершённые этапы с совпадающими параметрами.
ASR пока сохраняется целиком после транскрипции: прерывание в середине ASR
потребует повторной транскрипции. Результаты отдельных LLM-запросов кешируются.
Для возврата к ревью без сети откройте сохранённый `report.json` через UI.

### Продолжение после ошибки бюджета контекста

Размер запроса проверяется по всему пользовательскому промпту, а не только по JSON
транскрипта. Начальный запрос планируется в пределах 22000 UTF-8 байт; до жёсткого
предела 27000 байт оставлен резерв для объяснения ошибки и исправления ответа.
Это консервативный байтовый бюджет приложения, не точное число токенов модели.
Полный исходный текст не обрезается: слишком большие окна PASS 1 и блоки PASS 2
делятся по предложениям с перекрытием, части кешируются отдельно.
В повторном запросе сокращаются служебный прошлый ответ и диагностическое сообщение;
полные ответы модели сохраняются в `*_attempts.json`.

Редактор сначала убирает самый дальний соседний контекст, не трогая текст самого
клипа. Если и целый клип без соседнего контекста слишком велик, он остаётся `pending`
с явной пометкой о необходимости ручной проверки — не считается автоматически проверенным.

После обновления перезапустите приложение и повторно нажмите «Анализировать видео»
с прежними параметрами: завершённые скачивание, ASR и окна анализа будут взяты из кеша.
Сохранённые отчёты с ручными решениями не переписываются.
Для диагностики сохранённого сбоя доступна утилита:

```powershell
.\.venv\Scripts\python.exe context_regression.py "data/AVbz4UzkeTw/analysis/6b9513381a3f14d2de8a" --block 1
```

Флаг `--live` дополнительно отправляет один проблемный запрос в Ollama. Результат
сохраняется как `context_fix_probe.json`, не заменяя рабочие отчёты/решения пользователя.

### Невалидные ответы модели и частичный отбор

Для новых запусков используется описанный ниже PASS 2A/2B. Обработка произвольных
пар `start_id/end_id` сохранена как legacy-режим для сравнения и старых регрессий.

Каждый предложенный клип проверяется отдельно: наличие ID, структура, оценка,
порядок границ и длительность. Валидные варианты сохраняются между попытками,
даже если в том же ответе есть короткие или неверные клипы. Их границы не растягиваются
механически. После трёх попыток невалидные предложения отклоняются, а обработка
переходит к следующему блоку. Сохранённые попытки могут быть разобраны повторно
без новых LLM-запросов; успешный фрагмент не теряется из-за соседнего ошибочного.

Если отбор не стал полностью корректным, отчёт содержит `analysis_complete=false`,
`analysis_warnings` и подробные причины в кеше частей (`rejected_candidates`).
UI показывает предупреждения в журнале и пометку о неполном отборе.
Редактор, который трижды вернул недопустимое решение, также не останавливает VOD:
исходный валидный кандидат остаётся `pending` с требованием ручного ревью.
Сетевые ошибки/Ollama offline и повреждённый кеш не маскируются под успешный анализ.

Повторный запуск с теми же параметрами возвращает сохранённый отчёт и ручные решения;
частичный отчёт не перезаписывается автоматически. Для сравнения другой LLM её можно
выбрать в UI — результаты будут сохранены в отдельном кеше.

```powershell
# Восстановить валидные варианты из трёх сохранённых попыток без вызова LLM:
.\.venv\Scripts\python.exe context_regression.py "data/AVbz4UzkeTw/analysis/6b9513381a3f14d2de8a" --block 1 --replay-invalid
# Продолжить весь сохранённый прогон до ревью, без финального рендера:
.\.venv\Scripts\python.exe context_regression.py "data/AVbz4UzkeTw/analysis/6b9513381a3f14d2de8a" --resume
```

Журнал продолжения — `resume_analysis.log`, итог — `resume_result.json` в папке кеша.
Текущий полный отчёт VOD: `data/AVbz4UzkeTw/analysis/tail_v1_3e8f9ee9adc2792f35e7/report.json`.
В нём 25 кандидатов для ручного ревью; отметка частичного отбора сохранена честно.

### Новый PASS 2: выбор из допустимых интервалов

По умолчанию `analyze()` использует `selection_method="intervals"`:

1. **PASS 2A:** модель предлагает до трёх перспективных начал на техническую часть.
   Разрешены только существующие `start_id`, для которых в тематическом блоке есть
   хотя бы один интервал нужной длины.
2. **Код:** `interval_builder.py` строит окончания по границам предложений, считает
   итоговую длительность с запасом, проверяет источник и лимиты. Интервалы, чьё
   содержимое длиннее максимума, исключаются: последнее предложение не подрезается.
3. **PASS 2B:** модель выбирает `interval_id` из JSON-schema enum либо `none`.
   Она не задаёт секунды и не вычисляет разницу времён. Тексты окончаний и рассчитанная
   длительность доступны в каталоге; общий исходный текст передаётся целиком для
   сравниваемых вариантов, с явным указанием, что продолжение не входит в короткие варианты.
4. Длинный каталог делится на порции по фактическому бюджету запроса. Все варианты
   либо предъявлены, либо явно записаны как слишком большие для целого контекста.
   Последние дают предупреждение о неполном отборе, а не молча исчезают.
5. Результат преобразуется в привычного кандидата (`candidate_id`, `start/end`,
   заголовок, score, `pending`). В UI виден исходный `interval_id` выбора модели.
   Редактор использует общую проверку интервала при правках. Запас уже записан в
   `end_padding` и при последующей подготовке/рендере второй раз не добавляется.

Новые отчёты/этапы хранятся в `data/<id>/analysis/iv1_<signature>/`, а старый кеш
PASS 1 переиспользуется по прежней сигнатуре. Смена запаса создаёт отдельный кеш
нового отбора. Старые отчёты и решения редактора не перезаписываются.
Внутри нового кеша есть `block_*/starts_*.json`, `options_*.json`, `end_*.json`,
audit-файлы и `selection.json` со статистикой. Для legacy-сравнения доступен вызов
`analyze(..., selection_method="legacy")`.

Проверка сохранённых проблемных блоков без ASR и рендера:

```powershell
.\.venv\Scripts\python.exe interval_probe.py "data/AVbz4UzkeTw/analysis/6b9513381a3f14d2de8a" --blocks 1 8 24
```

Индексы аргумента начинаются с нуля: команда проверяет блоки 2, 9 и 25.
Результаты/логи — `data/validation_runs/intervals_v1_*/`. Повторный вызов использует
кеш и сохраняет первый замер времени отдельно от времени чтения кеша.
Утилита создаёт отдельный **тестовый** отчёт для UI, явно отмеченный как отбор
только выбранных блоков. Это не результат нового анализа всего VOD и не ручное утверждение.

## Профили выхода (16:9 хайлайты / 9:16 Shorts)

Приложение поддерживает два независимых формата выхода: горизонтальные хайлайты
(`format: "highlight"`) и вертикальные Shorts (`format: "short"`). Они отличаются
соотношением сторон, диапазоном длительностей, режимом кадрирования и субтитрами.

### Секция `outputs` в `config.json`

Параметры профилей задаются в секции `outputs`. При её отсутствии применяются
дефолты: хайлайты 120–300 с, запас 0,5 с; Shorts выключены.

```json
{
  "outputs": {
    "highlights": {
      "aspect_ratio": "16:9",
      "min_duration_sec": 120,
      "max_duration_sec": 300,
      "end_padding_sec": 0.5
    },
    "shorts": {
      "enabled": false,
      "aspect_ratio": "9:16",
      "min_duration_sec": 20,
      "target_duration_sec": 40,
      "max_duration_sec": 60,
      "crop_mode": "center",
      "subtitles_enabled": true,
      "max_candidates": 30,
      "final_candidates": 10
    }
  }
}
```

Поле `outputs` не обязательно: существующие `config.json` без него продолжают
работать, как и раньше, в режиме 16:9 с отключёнными Shorts.

### Отличия профилей

| Параметр | Highlights | Shorts |
|---|---|---|
| Отношение сторон | 16:9 (полный кадр) | 9:16 (кроп) |
| Мин. длительность | 120 с | 20 с |
| Целевая длительность | — | 40 с |
| Макс. длительность | 300 с | 60 с |
| Кроп | не применяется | `center` / `speaker` / `auto` |
| Субтитры | нет | да |
| Префикс ID кандидата | `c` | `s` |

### Независимые утверждения

Существующий `approval_key` (хеш от `candidate_id`, `start`, `end`) остаётся
неизменным и применяется только к хайлайтам. Для Shorts введён отдельный
`shorts_approval_key`, который дополнительно включает параметры рендера:
`crop_mode`, `crop_x`, `subtitles_enabled`, `output_width`, `output_height`
и `end_padding`. Изменение любого из этих параметров снимает утверждение Short.
Заголовок в сигнатуру не входит.

Два формата имеют независимые состояния утверждения: утверждённый хайлайт
не влияет на утверждение соответствующего Short и наоборот.

### Миграция старых отчётов

При открытии любого `report.json` через `open_report()` применяется
`migrate_report()`: кандидатам без поля `format` добавляется `format: "highlight"`,
отчёту добавляется секция `profiles`. Границы, утверждения и решения редактора
не изменяются. Повторное сохранение отчёта сохраняет дополненные поля.

### Текущий статус (Stage 3)

Реализованы: нормализация профилей, структура данных кандидатов, миграция
отчётов, независимые approval-ключи, **независимый PASS Shorts**
(`shorts_selector.py`) и тесты совместимости.

**PASS Shorts** работает параллельно с PASS 2A/2B для хайлайтов:
- Каталог Shorts-интервалов (20–60 с) строится и кешится отдельно.
- PASS 2A-Shorts: модель выбирает до трёх сильных начал.
- PASS 2B-Shorts: модель выбирает `interval_id` из enum каталога или `none`.
- Дедупликация по IoU ≥ 0.30.
- Кеш: `analysis/shorts_<signature>/block_*/`.
- Кандидаты получают `format: "shorts"` и префикс ID `sc`.

**Не реализовано** (следующие стадии): FFmpeg-кроп и масштабирование 9:16,
субтитры, UI-элементы выбора профиля и отображения Shorts-кандидатов.

## Текущие ограничения MVP

- Тематическое объединение использует взаимные флаги продолжения из PASS 1;
  embeddings ещё не подключены. Оценка и сортировка выполняются по LLM score,
  дополнительно применяется редакционная проверка кандидатов.
- Размер тематического блока ограничен с перекрытием. На длинных темах возможно
  потерять дальний контекст; редакционная проверка обязательна. Дополнительно
  измеряется полный запрос с инструкциями/метаданными и резервом повторных попыток;
  большие технические части делятся по предложениям.
  Для чата запрашивается контекст 32768 токенов; thinking отключён, если модель это поддерживает.
- Пунктуационные/паузовые границы предложений получены из ASR и могут ошибаться.
- Длительность проверяется кодом; завершённость смысла — моделью и редактором.
- Нет отмены текущей операции из UI. Окно остаётся отзывчивым, но штатное закрытие
  во время обработки заблокировано. HTTP-запрос к LLM ограничен 10 минутами.
- YouTube может потребовать дополнительные настройки yt-dlp, cookies или JS runtime;
  ошибки показываются в журнале. Автоматического обхода ограничений нет.

## Известное ограничение восстановления

- `report.json` с `analysis_complete=False` повторно используется без пересчёта:
  при повторном запуске анализа существующий отчёт загружается как есть,
  неполные блоки не пересобираются.
- Маркеры `validation_failed` в кеше (`starts_*.json`, `end_*.json`, `catalog.json`)
  не повторяются автоматически: при обнаружении маркера LLM-запрос не выполняется,
  часть отбора остаётся пропущенной.
- После временной ошибки LLM часть кандидатов может отсутствовать в финальном отчёте.
- Ручное удаление `report.json` опасно: теряются approvals, статусы и редакторские
  правки, внесённые пользователем до удаления.
- Механизм безопасного повтора только неудачных запросов (retry_failed) отложен
  на будущее и не реализован.

## Stage 4 — Редакционная проверка Shorts

Независимая редакционная проверка Shorts-кандидатов (модуль `shorts_editorial.py`).

**Критерии проверки:**
1. **Сильное начало** — первые 1–3 секунды цепляют, нет долгого вступления
2. **Самодостаточность** — понятен без предшествующего контекста стрима
3. **Завершённость** — есть вывод или чёткая остановка, не обрывается
4. **Одна тема** — внутри Short нет смены предмета разговора
5. **Нет лишней паузы** — в начале и конце нет затянутого молчания
6. **Не фрагмент** — это не кусок большой истории, требующий контекста

**Механизм:**
- Вызывается автоматически после `select_shorts` в `analyzer.py`
- Использует `transcript_review.review_sections` для контекста вокруг границ
- Кеш: `analysis/shorts_{signature}_editorial_v1_{model_key}/`
- Решения: `keep` (сохранить), `revise` (исправить границы), `reject` (отклонить)
- При `revise` — границы сдвигаются, `approval_key` удаляется (требуется повторное утверждение)
- При ошибке LLM — `editorial_decision: "needs_review"`, кандидат сохраняется
- Утверждённые кандидаты (`status: "approved"`) не перепроверяются
- Дедупликация по IoU ≥ 0.30 после редакционной правки

**Независимость от Highlights:**
- Отдельный кеш, отдельная схема JSON, отдельные поля в отчёте
- Утверждения Highlights не затрагиваются
- Изменение границ Shorts не влияет на Highlights и наоборот

**Поля кандидата после проверки:**
- `editorial_decision`: `"keep" | "revise" | "reject" | "needs_review"`
- `editorial_flags`: объект с 6 boolean-флагами критериев
- `score`: обновлённый балл 0–100
- `title`, `reason`: от LLM-редактора
- `warnings`: список предупреждений (если были проблемы)

**Тесты:** `test_shorts_editorial.py` (8 тестов)

## Stage 5 — UI интеграция Shorts 9:16

Интерфейс поддерживает два формата выхода через Notebook-вкладки.

### Структура UI

- **Вкладка "Хайлайты 16:9"** — существующая таблица кандидатов для горизонтальных клипов
- **Вкладка "Shorts 9:16"** — новая таблица кандидатов для вертикальных Shorts

Каждая вкладка имеет свою таблицу с колонками:

## Subs Settings — оформление субтитров Shorts

Кнопка **Subs Settings** открывает отдельное неблокирующее окно (повторное нажатие
поднимает существующее). Настройки влияют **только на Shorts**, если у кандидата
включены субтитры. Highlights остаются без вшитых субтитров.

- **Font** — семейство установленного Windows-шрифта. Если шрифт из пресета отсутствует,
  редактор показывает предупреждение, а libass выбирает доступную замену; можно выбрать Arial.
  Перечень Tk/Windows и выбор шрифта libass могут отличаться, особенно для отдельных символов.
- **Font Size** — 1–144 единицы ASS при `PlayRes=384×288`, не пиксели видео.
  Историческое значение — 18. Результат масштабируется на итоговые 1080×1920.
- **Position X/Y** — дробные проценты кадра, от левого/верхнего края.
  Изменение X/Y переключает позиционирование в `free`: якорь — центр текстового блока.
  У границ кадра координаты консервативно ограничиваются по оценке размера текста;
  переносы выполняет libass. Для необычно широких шрифтов/очень крупного текста оценка
  не является точным измерением глифов: проверяйте крайние позиции в предпросмотре.
- **historical** — исходное нижнее выравнивание и отступы; X/Y в этом режиме не используются.
- **Прямоугольная подложка** включается отдельно. Цвет `#RRGGBB` и непрозрачность
  0–100% управляют только подложкой; текст остаётся белым.
- **Обводка текста** — чекбокс включения/отключения и HEX-поле/палитра цвета обводки.
  Историческое значение — включена, чёрная; толщина остаётся 1 ASS. Подложка независима
  от обводки и не исчезает при её отключении.
- **Ширина / Высота области (%)** — дробные значения от 1 до 100% итогового кадра.
  Изменение размера автоматически включает **«Ограничить область субтитров»** и режим `free`.
  Якорь X/Y — центр области; если область выходит за кадр, она сдвигается внутрь целиком.
  Ширина задаёт перенос строк, за границами области текст, обводка и подложка обрезаются.
  **Размер шрифта не уменьшается и не меняется от реплики к реплике.** Низкая область
  может обрезать строки и части букв — это намеренное поведение.
  Желтая рамка показывает границы только в предпросмотре, в итоговый MP4 она не попадает.
  Без ограничения области остаётся прежнее позиционирование и переносы. В defaults
  ограничение выключено; неактивные размеры — 68,75% ширины и 100% высоты.
  Выбор `historical` отключает ограничение области и восстанавливает прежний способ позиции.

**Subtitle Preview** — настоящий одиночный синтетический кадр FFmpeg/libass,
генерируется в фоновом потоке после изменения полей без исходного видео и полного рендера.
Кадр уменьшается до 270×480, поэтому мелкие детали сглаживаются. Это пример двух строк,
а не гарантия идентичной геометрии для любого текста; доступность FFmpeg обязательна.

Кнопки работают независимо:

- **Save** экспортирует валидный JSON-пресет по выбранному пути, не активируя его.
- **Load** целиком загружает валидный пресет в поля, не активируя его.
- **Set Default** восстанавливает исторические значения в полях, не активируя их.
- **Применить** атомарно сохраняет активные настройки в `data/subtitle_settings.json`.
  Они восстанавливаются при следующем запуске. Повреждённый файл не перезаписывается:
  приложение сообщает об ошибке и использует исторический стиль до явного применения.

Пример пресета (такой же формат у активных настроек):

```json
{
  "schema_version": 2,
  "shorts": {
    "font": "Arial",
    "font_size": 18,
    "position_mode": "free",
    "x": 50,
    "y": 75,
    "background_enabled": true,
    "background_color": "#000000",
    "background_opacity": 70,
    "outline_enabled": true,
    "outline_color": "#000000",
    "area_enabled": true,
    "width_percent": 68.75,
    "height_percent": 20
  }
}
```

Новые поля сохраняются и в экспортируемых пресетах, и в активном конфиге
`data/subtitle_settings.json`, а также в метаданных экспорта MP4. Старые файлы схемы v1
загружаются без изменения прежнего оформления: чёрная обводка включена, ограничение
области выключено. При следующем явном сохранении/применении записывается схема v2.

Исторические defaults: Arial, ASS FontSize 18, белый текст, чёрная обводка 1,
`Alignment=2`, `MarginV=240`, `MarginL=MarginR=60`. Проверенная конвертация SRT
в установленном FFmpeg: `PlayResX=384`, `PlayResY=288`, `BorderStyle=1`, `Shadow=0`.
Прямоугольной подложки нет. Неактивные параметры подложки: чёрный, 100%; X=50,
Y≈16,667 — справочная координата исторического нижнего якоря, а не центр блока.
Set Default + Применить возвращает **исходный SRT force_style без изменений**.

Оформление не меняет ASR, анализ, текст, тайминги, Smart Crop или утверждённые границы.
Каждое задание получает неизменяемый снимок стиля до запуска рабочего потока.
Новая стилизация относится к будущим экспортам, существующие MP4 не изменяются.
В JSON рядом с новым MP4 записывается использованный стиль. Исходный SRT сохраняет текст
и тайминги; пользовательский ASS создаётся только во временном файле и затем удаляется.

Проверки: `python -m unittest test_subtitle_settings -v` (включая GUI, реальный
синтетический MP4, изменение пикселей при настройках и попиксельную совместимость defaults).

## Stage 6 — Рендер Shorts 9:16

Рендер вертикальных Shorts 9:16 через FFmpeg.

### Окно «Настройки Shorts» — разрешение и сжатие

Кнопка **«Настройки Shorts»** находится рядом с **Subs Settings**. Она открывает
отдельное неблокирующее окно; повторное нажатие поднимает уже открытое.

Два независимых параметра:

| Параметр | Варианты |
|---|---|
| Разрешение | 720p — 720×1280; 1080p — 1080×1920; Оригинальное |
| Сжатие | Высокое качество — CRF 18; Баланс — CRF 23; Компактное — CRF 28 |

**По умолчанию сохраняется прежний рендер: 1080×1920, CRF 18.**
Нажмите **«Применить»**, чтобы сделать значения активными и сохранить их в
`data/shorts_render_settings.json`. Поля окна — черновик: закрытие без применения
не меняет активные значения. Кнопка **«По умолчанию»** восстанавливает значения
в полях, для их активации также нужно нажать «Применить».

При следующем запуске активные настройки читаются из файла. Повреждённый/неподдерживаемый
JSON вызывает предупреждение и возврат к 1080p / CRF 18, но не перезаписывается автоматически.

```json
{
  "schema_version": 1,
  "shorts_export": {
    "resolution": "720p",
    "compression": "balanced"
  }
}
```

Допустимые значения: resolution — `720p`, `1080p`, `original`; compression —
`high`, `balanced`, `compact`.

Настройки используются как для кнопки **«Рендер все Shorts»**, так и для рендера
одного кандидата. При старте задания фиксируется неизменяемый снимок активных значений:
смена настроек во время обработки относится только к следующим заданиям.
Открывать окно перед каждым рендером не требуется.

**«Оригинальное»** — наибольший вертикальный кадр 9:16, вписанный в разрешение
исходника, с округлением до чётных размеров для H.264. Например, из 3840×2160
получится 1216×2160, из 1920×1080 — 608×1080. Незначительное отклонение от 9:16
возможно из-за округления. Это не копирование потока: кроп, субтитры и H.264-кодирование
по-прежнему выполняются. При увеличении в Smart Crop выбранная область масштабируется
до выходного разрешения; размеры экспорта постоянны для всех сегментов одного Short.

Для меньшего веса рекомендуется начать с **720p + «Баланс»**. Меньшее разрешение и
более высокий CRF обычно уменьшают файл, но размер в МБ не гарантирован: он зависит
от деталей, движения и длительности. Фиксированные 720p/1080p могут увеличивать низкое
разрешение источника. Аудио остаётся AAC 192 кбит/с; видеокодек — H.264, preset slow.

Экспортные параметры не меняют анализ, утверждённые интервалы или Smart Crop.
Highlights не затрагиваются. Использованные режимы, CRF и фактическое разрешение
записываются в поле `export_settings` JSON рядом с новым MP4. Существующие результаты
не перезаписываются. Стили субтитров масштабируются относительно выходного кадра.

### Архитектура

**Модуль `renderer.py`:**

- `render_shorts_approved(manifest, report, job_dir, log, transcript=None, candidate_id=None, subtitle_settings=None, export_settings=None)` —
  основной рендер утверждённых Shorts-кандидатов. Возвращает список путей к MP4.
- `shorts_approval_key(candidate)` — хэш для проверки актуальности утверждения. Учитывает:
  `candidate_id`, `start`, `end`, `format`, `crop_mode`, `crop_x`, `subtitles_enabled`,
  `output_width`, `output_height`, `end_padding`.
- `_crop_params(source_width, source_height, crop_x=None)` — вычисляет параметры crop= для 9:16 области.
- `validate_crop_x(value)` — валидация crop_x (0.0–1.0).
- `build_subtitles_srt(transcript, clip_start, clip_end)` — генерация SRT из word timestamps.
- `_group_words_into_cues(words, max_words=6)` — группировка слов в подсказки по 4–6 слов.
- `_srt_timecode(seconds)` — форматирование таймкода SRT.
- `_probe_basic(path)` — упрощённый ffprobe для проверки результата рендера.

### Параметры рендера

- **Выход:** выбранные в «Настройки Shorts» разрешение и CRF; по умолчанию 1080×1920,
  CRF 18, H.264/AAC. Выходное разрешение проверяется через ffprobe.
- **Кропирование:** по умолчанию центрированное; `crop_x` (0.0–1.0) для смещения.
- **Субтитры:** SRT из word timestamps Whisper, синхронизированы с утверждённым интервалом.
- **Безопасность файлов:** отдельные папки `shorts/` и `highlights/` в выходном каталоге.

### Логика утверждения

- `shorts_approval_key` вычисляется из ключевых параметров кандидата.
- Изменение границ, crop_x или subtitles_enabled инвалидирует утверждение.
- Рендер проверяет соответствие `approval_key` и отклоняет устаревшие утверждения.

### Интеграция с UI

- `review_ui.py`: `render_shorts()` вызывает `render_shorts_approved()` с фильтрацией по кандидату.
- Таблица Shorts: кнопка «Рендер» в строке кандидата вызывает рендер конкретного Short.
- Кнопка «Рендер все Shorts» в строке кнопок вызывает рендер всех утверждённых.

### Тесты

`test_shorts_settings.py`: модель и JSON, GUI, сохранение/перезапуск, снимок настроек
для одиночного и пакетного рендера, обычный и одно-/многосегментный Smart Crop,
реальный FFmpeg-рендер всех девяти сочетаний разрешения/сжатия с субтитрами.

`test_shorts_render.py` (39 тестов):

# Подсветка текущего слова в Subs Settings

Включите «Менять цвет текущего слова» и задайте «Цвет текущего слова» через поле `#RRGGBB` или палитру. По умолчанию функция выключена, цвет — жёлтый `#FFFF00`.
Вся реплика отображается белым; только произносимое слово меняет цвет по таймингам транскрипта. После окончания слова цвет возвращается к белому, в паузах подсветки нет. Точность ограничена таймингами ASR и сотыми секунды формата ASS. Предпросмотр показывает выделение первого слова на статичном примере.
Параметры сохраняются в пресетах версии 3; пресеты версий 1 и 2 загружаются с выключенной подсветкой. Нажмите «Применить» для использования в будущих Shorts.
# Ручное исправление реплик

В панели реплик дважды щёлкните по строке с таймкодами. В отдельном окне исправьте текст полной реплики и нажмите «Внести в правки». Это черновик: для записи в JSON-отчёт нажмите существующую кнопку «Сохранить правки / на доработку» либо «Утвердить интервал». Отмена закрывает редактор без внесения изменений. Пустой текст не допускается.

Правки относятся к выбранному кандидату (Highlights или Shorts), сохраняются при повторном открытии отчёта и используются в экспортируемом тексте; в Shorts также в SRT и вшитых субтитрах, включая подсветку слов. После сохранения на доработку требуется повторное утверждение. Горизонтальные Highlights сохраняют исходный звук и кадр; исправление транскрипта не меняет произнесённую речь.

Тайминги неизменённых слов сохраняются. Заменённые/добавленные слова распределяются внутри соответствующего участка реплики; если паузы для вставки нет, используется часть времени соседнего слова. Это приблизительная разметка, без повторного ASR. В неполной реплике редактируется полный текст, но в субтитры попадает только участок внутри границ клипа. Исходный ASR-кеш остаётся сохранённым; соседние кандидаты используют свои правки.
