## Цель

Добавить создание вертикальных Shorts 9:16 как **второй независимый профиль** поверх
существующей системы горизонтальных хайлайтов 16:9, сохранив совместимость с текущим
сценарием. Shorts и хайлайты разделяются только на уровне выбора кандидатов, настроек
и рендера; источник, транскрипт и PASS 1 используются совместно.

## Текущая архитектура (факт)

Пайплайн разделён на модули, каждый с одной ответственностью. Ключевые потоки:

```
YouTube URL
  → downloader.download()        скачивает source.mkv, пробует ffprobe (проверка 16:9)
  → app_backend.ensure_transcript()  → transcriber.transcribe()  (Faster-Whisper, CUDA)
  → app_backend.ensure_analysis()
       → analyzer.analyze()      PASS 1: смысловые группы (LLM)
       → interval_selector.select_intervals()
             PASS 2A: выбор начал (LLM)
             PASS 2B: выбор интервалов (LLM)
       → editorial_review.review_candidates()   независимая редакционная проверка (LLM)
  → job_store.save_report()       атомарная запись report.json + транскрипт
  → review_ui.ReportReview        таблица, правки, утверждение, предпросмотр FFplay
  → renderer.render_approved()    FFmpeg: нарезка утверждённых интервалов 16:9
```

Ключевое свойство: **формат выходного видео (16:9, без кропа) жёстко заложен** в
`renderer.py` и `downloader.py`, а не вынесен в конфигурацию. Это главное место, где
придётся добавить ветвление на профиль.

## Найденные точки расширения

### 1. Формат 16:9 — жёстко закодирован

| Файл | Местоположение | Что делает |
|---|---|---|
| `renderer.py:1` | docstring | «preserve the full 16:9 frame» |
| `renderer.py:80` | `render_approved()` | FFmpeg-команда: точная нарезка, `-c copy`, без crop/scale |
| `downloader.py:24-25` | `probe()` | Бросает `ValueError` если ratio ≠ 16/9 ± 0.02 |
| `review_ui.py:26` | `__init__` | Заголовок окна: «горизонтальные хайлайты 16:9» |

Для Shorts 9:16 нужен `crop=ih*(9/16):ih:(iw-ow)/2:0` в FFmpeg-фильтре рендера.
Текущий код в `renderer.py` использует `-c copy` (без перекодирования), поэтому
для вертикального кропа потребуется перекодирование (`libx264`) и изменение фильтра.

### 2. Отсутствует понятие «профиля»

В `config.json`, `job_store.py`, `app_backend.py` нет поля `profile`, `aspect_ratio`
или `crop_mode`. Все кандидаты рендерятся одинаково. Для двух независимых профилей
нужно:

- Добавить в `report.json` поле профиля (например `"profile": "horizontal_16_9"`
  или `"profile": "vertical_9_16"`).
- Разделить выход: `output/<signature>/` для 16:9 и `output/<signature>/shorts/`
  для 9:16 (согласно `Shorts_Pipeline.md` §7).
- Сохранить совместимость: отсутствие поля профиля в старых отчётах трактуется
  как `"horizontal_16_9"`.

### 3. Выбор кандидатов — общий или раздельный?

`Shorts_Pipeline.md` §3 говорит: «Shorts и хайлайты разделяются только на уровне
выбора кандидатов, настроек и рендера». Это означает:

- **Общее:** `source.mkv`, транскрипт, PASS 1 (семантические группы).
- **Раздельное:** настройки длительности (Shorts обычно 30–90 с, хайлайты 120–300 с),
  PASS 2A/2B (выбор разных интервалов), редакционная проверка, утверждение, рендер.

В текущем коде `interval_selector.py` и `editorial_review.py` не знают о профиле —
они работают с единым списком кандидатов. Для разделения нужно передать профиль
в эти функции или создать два независимых прогона PASS 2 с разными параметрами
длительности.

### 4. Настройки в `config.json`

Текущая структура не имеет секций по профилям. `Shorts_Pipeline.md` §2.1 предлагает
вложенную схему `outputs.{highlights,shorts}`. Пока в `config.json` плоская структура:
`min_duration_sec`, `max_duration_sec`, `end_padding_sec` без привязки к формату.

### 4.2. Утверждения: независимые сигнатуры двух форматов

Существующий `approval_key` в `renderer.py:13` хеширует только
`(candidate_id, start, end)`. Его **сохранить без изменений** для старых хайлайтов —
это требование обратной совместимости (§2.5: «корректную работу существующих утверждений»).

Для Shorts ввести **отдельную** функцию `shorts_approval_key(candidate)`, учитывающую
всё, что влияет на итоговый MP4 (§2.4):

```
shorts_approval_key = sha256(
    candidate_id,
    start, end,
    end_padding_sec / end_padding (итоговая граница после запаса),
    crop_mode, crop_x,
    subtitles_enabled (+ идентификатор содержимого/стиля субтитров, когда появится),
    выходное разрешение (1080×1920)
)
```

Принципы:

- Изменение любого перечисленного параметра ⇒ новый хеш ⇒ снятие утверждения Short.
- Утверждение Short **не влияет** на утверждение длинного хайлайта и наоборот
  (независимые поля, разные функции).
- Изменение только `title`/имени файла **не меняет** ни один из хешей (название не входит
  в сигнатуру) — метаданные отделены от видеосодержимого, как требует §2.4.
- Функция детерминирована: тот же кандидат ⇒ тот же хеш.

Выбор: не расширять старый `approval_key`, а добавить вторую функцию, чтобы старые
отчёты и их утверждения продолжали валидизироваться прежней формулой.

### 4.3. Хранение кандидатов двух форматов

Рассмотрены два подхода; **выбран первый**, без изменения существующего механизма:

**Подход A (выбран): один отчёт, раздельные ветки кандидатов.**
Все кандидаты живут в одном `report.json`, поле `format` различает их:
отсутствует или `"highlight"` → длинный хайлайт, `"short"` → Shorts.

- Общее (один `report.json`): `video_id`, `settings`, транскрипт, PASS 1, `signature`.
- Раздельное (внутри отчёта): списки кандидатов по `format`, их статусы,
  утверждения (`approval_key` / `shorts_approval_key`), `render_settings`,
  пути экспорта (`output/<signature>/` и `output/<signature>/shorts/`).
- Идентификаторы в **разных пространствах**: хайлайты `c001…` (как сейчас),
  Shorts `s001…` — уникальность гарантируется префиксом (§2.3).
- Связь с исходником: оба профиля ссылаются на один `source.mkv`/транскрипт через
  общий `video_id` и `job_dir`; дублирования источника нет.

Почему A, а не связанные отдельные отчёты (Подход B): существующий пайплайн
уже сохраняет один `report.json` на прогон анализа с общим PASS 1. Подход B потребовал
бы дублировать транскрипт/PASS 1 или вводить механизм ссылок между отчётами — больший
объём изменений и риск рассинхронизации. Подход A переиспользует всё существующее
(`job_store`, `renderer`, кеш) и добавляет только поле `format` + вторую ветку рендера.

Компромисс A: в одном файле два списка. Митигация — строгие префиксы ID
(`c`/`s`) и валидация, что префикс соответствует `format`; UI (Stage 5) отфильтрует
ветку по вкладке. На Stage 2 это только данные — рендер/UI не трогаются.

### 5. UI — единое окно, один набор кандидатов

`review_ui.py` управляет одной таблицей кандидатов и одним набором настроек
длительности. Для двух профилей нужно либо:

- **Вариант A:** переключатель профиля вверху окна, при переключении меняется
  набор кандидатов и настройки (требует два отчёта или два набора полей в отчёте).
- **Вариант B:** отдельные кнопки/вкладки «Хайлайты 16:9» и «Shorts 9:16»,
  каждая со своей таблицей.

`Shorts_Pipeline.md` §6 описывает вкладки, что ближе к Варианту B.

### 6. Рендер — ключевое отличие по формату

`renderer.py:render_approved()` (строка 80):

```python
command = ["ffmpeg", "-y", "-hide_banner", "-loglevel", "error",
           "-ss", f"{start:.3f}", "-to", f"{end:.3f}",
           "-i", str(source), "-c", "copy", "-avoid_negative_ts", "1", str(target)]
```

Для Shorts 9:16 нужно:

- Заменить `-c copy` на перекодирование: `-c:v libx264 -crf 18 -preset medium -c:a aac`.
- Добавить фильтр: `-vf "crop=ih*(9/16):ih:(iw-ow)/2:0,scale=1080:1920"` (или без
  scale, если сохраняем исходные пиксели 405×720).
- Указать выходное разрешение в метаданных.

Важно: `approval_key` (хеш утверждённых границ) не должен меняться от формата —
утверждённые границы одни для обоих профилей, меняется только способ нарезки.
